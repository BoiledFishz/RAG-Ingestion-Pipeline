## Core Principles

### I. Evidence Before Claims (NON-NEGOTIABLE)
Every number in a spec, comparison, improvement note or PR MUST trace to a file under
`evaluation/results/` (or the tune folder for design studies) produced by a recorded command.
Anything not executed is written as **未执行 / not executed** with the reason. Dates are never
back-filled, and work reviewed after the fact is labelled post-hoc.
Rationale: course grading and reviewers rely on the record, not on the narrative.

### II. Split Discipline
Thresholds, refusal signals, retrieval parameters and default switches are chosen ONLY on the
tune split (seed 20261012) by a rule written down before the run. The evaluation split
(seed 20261011) is for reporting only. A confirmation split is run exactly once for a frozen
configuration; when the configuration changes after that run, a new confirmation split is built.
Rationale: otherwise reported gains are fitted to the test data.

### III. Reuse Without Modification
Project 1 code, the original `api.main` and the old MultiAgentVersion MUST NOT be modified.
Extensions use wrapping, subclassing or dependency injection, and are tested at that seam.
Rationale: the baseline must stay reproducible for comparison.

### IV. Program-Owned Authority
Permissions come only from server-side credentials (TrustedContext), never from request bodies
or model output. There is no Text-to-SQL: SQL text is owned by registered templates with typed
parameters. A model may only choose among program-built options, and the program validates the
choice. Authorization is applied at retrieval time, before ranking and before any model sees
data; denials never reveal whether data exists.
Rationale: model output and user input are untrusted.

### V. Bounded Execution
Every request has a deadline and per-kind call caps (LLM, embedding, DB, tool, SQL, local
compute), reserved before each call; retries and replans are bounded and counted. A failure is
never upgraded to success: merged status follows the six-state rules.
Rationale: predictable cost and termination.

### VI. Versioned Contracts
Worker inputs/outputs are explicit schemas with a `CONTRACT_VERSION`. Any field, operation or
semantic change bumps or records the version in `contract_changelog.md` with its reason.
Rationale: Supervisor and Workers evolve independently.

### VII. Reproducible Artifacts
Data samples, task sets and indices are generated by seeded commands; uncommitted artifacts have
pinned content digests and a rebuild-and-verify command. Results record git commit, model
digests, versions and configuration.
Rationale: anyone can regenerate and check the evidence.

## Security & Data Constraints
- Secrets and bearer tokens never enter the repository; credentials are stored as SHA-256 hashes.
- Uncommitted working-tree changes of other work are isolated (git worktree or stash) and never
  mixed into a feature commit.
- Logged or returned errors carry categories, not stack traces or SQL.

## Development Workflow & Quality Gates
1. Spec (`/speckit-specify`) → human review of the spec → plan → tasks → implementation.
   Reviews are recorded with date and reviewer in `review_log.md`.
2. Each completed task is committed and logged in `tasks.md` with: change, commands run, actual
   results.
3. Gates before a PR: tests pass; ruff clean; mypy clean for touched files; contract changelog
   updated; comparison numbers regenerated from results.
4. A PR is merged only after review by someone other than its author; authors and agents never
   self-merge.
