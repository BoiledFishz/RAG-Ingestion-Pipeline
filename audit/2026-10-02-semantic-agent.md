## Agent 改进

- 模型只选择有限的证据 ID，程序从原始 TechQA 文档渲染答案及引用。
- 选择结果要求严格布尔类型、合法 ID、充分性与 ID 列表一致；格式错误只修复一次。
- 拒答、输出验证失败与模型不可用分别处理。服务故障不算知识库拒答成功。
- 压缩保留完整解答段落；版本/暴露问题优先保留“受影响产品和版本”。
- 检索窗口可能从单词中间开始；回答抽取先恢复 Parent 的段落边界，保留命中位置权重。
- 分批判断证据，限制标题长度和 ReAct 每轮观察文档数，控制模型上下文。
- Planner 的实际 DAG 驱动执行；专家答案正文保留，引用在合并时重新映射。
- Planner 校验每条最终输出路径经过 Diagnosis/Critic；不能把未复核的新检索分支并入报告。
  格式合法但绕过复核的计划也必须由模型修正，执行器另行校验。
- Critic 使用简单严格输出；最多重试两次。后续 Critic 真正通过才记录问题已解决。
- 生产 Diagnosis 与 Critic 分批检查原文充分性；复核只读取答案所引证据的上下文，拒答则检查全部候选。
- 模型依赖故障返回 HTTP 503，不记为知识库拒答成功；非法/超长来源上下文在模型调用前返回 422。
- `answer_sufficient` 必须同时满足复核通过、非空正文和非拒答，不能把失败诊断标成充分答案。
- 引用及错误码/CVE/精确版本另由程序校验；Critic 最终未通过则阻止发布答案，失败状态传递至报告节点。
- 答案分数只使用正文，并要求正文实际引用官方参考文档；sources 字段不贡献得分。
- 没有检索证据时跳过模型，并记录 `run=null`；不能制造 Critic 通过记录。
  此类样本仍计入正文质量分母，检索故障与空结果尚无法完全区分时不计拒答成功。

这些措施降低错误输出风险，并不等于已经证明所有自由文本事实均正确。
