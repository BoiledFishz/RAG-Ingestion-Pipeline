A. 预算上限基于实测
1. 先从 audit/project2-v1/native_gate_round2.json 等证据确认 AC12-01 的 RAG timeout 究竟由哪一项触发
   （依赖尝试上限、LLM 尝试上限，还是墙钟超时），写入 delta.md。
2. 写清"一次依赖尝试"的计数口径。口径不得为了让数字变小而重新定义；
   只有能证明原口径把同一批次不合理地拆成逐条计数时才可调整，并记录理由。
3. 标定：只用 tune，按已登记的抽样规则，对 RAG 单独路径和组合路径各跑完整的已登记组合任务集，
   记录每个请求的依赖尝试数、LLM 尝试数、耗时。
4. 新上限 = 实测 p95 向上取整后加 25% 余量；墙钟超时 = 实测 p95 的 1.5 倍。上限仍是硬上限，在默认 API 路径强制。
5. 熔断条件：若实测 p95 的依赖尝试超过 32 或 LLM 尝试超过 12（均为现有上限的 2 倍），
   不要放大上限，停止并报告，说明 RAG 路径需要先做结构性精简（如合并批量调用）。
6. 预算耗尽类场景（AC12-01、AC12-15、AC12-16）的数值按新上限更新，故障注入测试保持，
   "第 N+1 次不启动"的断言保持。标定协议、结果与哈希冻结。
